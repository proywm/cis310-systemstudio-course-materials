SystemStudio CIS 310: setup and first tasks

Shortest path: open the SystemStudio activity-bar icon, expand Course Modules, and follow one module’s Accessible lesson → Read → Watch → Practice → Build/debug path. Use Canvas for official instructions, submission, receipts, and instructor evaluation.

2. Why “Docker Desktop is not running” appears

Your circuit is safe and was not changed. The message is about the simulator runtime, not the .dig file.

Digital is a Java/Swing desktop application. A VS Code webview cannot directly host a native Swing window. On Windows and macOS, SystemStudio starts the complete upstream Digital application inside a course container, then streams that private desktop into the tab. Seeing the Docker command on the computer only proves that the client is installed; the background Docker engine must also be running.

The Windows text open //./pipe/docker_engine: The system cannot find the file specified means the expected Docker engine named pipe does not exist yet—usually because Docker Desktop is closed or still starting.

  1. Open Docker Desktop from the Start menu.
  2. Wait until Docker Desktop reports that its engine is running. The first startup can take a minute.
  3. Return to the Digital tab and choose Retry embedded Digital.
  4. If it still fails, run CIS 310: Check Environment and retain the expandable technical detail when requesting help.

Use Open verified native Digital only when the button is shown. That button appears only when the pinned Digital installation, a supported Java runtime, and a local graphical desktop are all available.

3. First circuit

  1. Open Hands-on Circuit and Assembly Labs and choose Build and verify a half adder.
  2. Write your prediction for Sum and Carry before wiring.
  3. Choose Create circuit. SystemStudio never overwrites an existing file; if a name exists, it creates a numbered sibling.
  4. In upstream Digital, place components, wire them, and test all four input combinations.
  5. Save the .dig file, then use Run Digital Circuit Tests or the assignment public preflight when one is provided.
  6. Explain expected versus observed evidence in your own words. A local pass is formative evidence, not an instructor grade or Canvas submission.

4. First assembly lab

  1. Run CIS 310: Create NASM Assembly Workspace.
  2. Open RegisterArithmetic.asm and predict the register values.
  3. Run CIS 310: Open Actual NASM Debug Workbench.
  4. Build/run, stop at an inspection label, then compare EAX–EDI, EFLAGS, stack, memory, Intel disassembly, program output, and exit status.
  5. Files named *.test.asm appear in VS Code’s Testing view and pass only when the assembled ELF32 program returns exit code 0.

Tool boundary: the optional Instruction Trace Tutor is a conceptual visualization. It does not assemble code, create machine-code evidence, or replace the NASM/GDB workbench.

5. Before submitting

  • Review the current Canvas assignment and rubric.
  • Run the smallest relevant unit test, then the published public preflight.
  • Add your own boundary and failure cases; public checks are not hidden grading tests.
  • Open the saved artifact again and verify it is the intended version.
  • Submit in Canvas and verify the Canvas submission receipt.

6. Getting help

Open Local FAQ Chat for course/tool routing. Use the AI learning coach only after an attempt and ask for one hint or diagnostic question; do not ask it to produce graded work.
